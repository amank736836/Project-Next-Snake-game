# BUG-017 — A rejected database connection is cached forever — the process never recovers

| Field | Value |
| --- | --- |
| Bug ID | `BUG-017` |
| Title | A rejected database connection is cached forever — the process never recovers |
| Severity | High |
| Priority | P2 |
| Feature | FEAT-008 |
| Environment | production build with `DATABASE_URL` set to an unreachable host |
| Status | OPEN |

**Preconditions:** A server started with a bad or unavailable `DATABASE_URL`.

## Steps to Reproduce

1. Call any endpoint — the first request fails after ~1.5 s
2. Call it again — the failure is fast
3. Bring the database up (or make the host reachable)
4. Call again — the API should recover

## Expected

The failure is cached for speed but retried later; recovery must not require a restart. (The stronger expectation asserted by TC-131b: fall back to the in-memory board rather than failing forever.)

## Actual

The rejected connection promise is cached in `globalThis`, so every later request awaits the same rejection forever — recovery requires a process restart.

## Reproducible

YES (TC-131, TC-131b).

## Evidence

`test-results/latest/database.tap` · `evidence/database-results/RUN-2026-001/*-degraded.txt`

## Root Cause

`src/lib/db.ts` stores `cached.promise` and reuses it without clearing it on rejection.

## Fix

Clear the cached promise on rejection (or cache only successful connections) and add a retry with backoff, keeping TC-131's fast-failure property.
