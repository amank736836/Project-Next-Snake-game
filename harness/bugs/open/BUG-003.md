# BUG-003 — The API accepts display names the UI forbids (length, characters, emptiness)

| Field | Value |
| --- | --- |
| Bug ID | `BUG-003` |
| Title | The API accepts display names the UI forbids (length, characters, emptiness) |
| Severity | Medium |
| Priority | P2 |
| Feature | FEAT-005, FEAT-007 |
| Environment | production build, demo storage |
| Status | OPEN |

**Preconditions:** Server running.

## Steps to Reproduce

1. POST a 5 000-character name
2. POST `""` and `"   "`
3. POST `<script>alert(1)</script>`
4. Read the board and inspect the echoed names

## Expected

400, or sanitisation to the documented UI rule: 1–20 characters of `[a-zA-Z0-9 ]`.

## Actual

Every payload is accepted. Names are echoed into leaderboard payloads unmodified; a 5 000-character name inflates a page from ~690 B to ~5.6 KB.

## Reproducible

YES (TC-069, TC-069b).

## Evidence

`test-results/latest/api.tap` (TC-069, TC-069b)

## Root Cause

`MissionHub.tsx` filters input in the browser; there is no server-side counterpart — the API trusts the client.

## Fix

Share one validator between the client and the route (`/^[a-zA-Z0-9 ]{1,20}$/` on the trimmed name) and reject anything else with 400.

TC-069 (`todo`, asserts the 400) and TC-069b (characterisation of today's behaviour).
